## 五、「708 个只下了 690 个」核查结论

实测口径（`download` 目录 + `config\repo.config` + `config\upall\checkpoint_634427163_*.json`）：

| 项目 | 数值 |
|---|---|
| 该 UP 主（UID 634427163）清单条目 | **732** |
| download 目录 mp4 文件 | **690**（2.67 GB） |
| 其中唯一 BV（视频数） | **688**（有 2 个视频各多下了 1 个分P） |
| `repo.config` 行数 | **690**（与文件数一一对应） |
| 清单里没有本地文件的 | **44 个 BV** |

`732 = 688（已下）+ 44（未下）`，账目闭合。台账同步后：在库 690 条、清单里剩 44 条。

**44 个的核查结果（不是视频失效）**：

1. 逐个请求 `api.bilibili.com/x/web-interface/view`，**44 条全部 `code=0 OK`、`state=0`**；
2. 抽 6 条用程序自己的 `INeedAV.getVideoDetail()` 实测，都能返回 8 档清晰度
   （120/116/112/80/74/64/32/16），不是会员、版权、清晰度问题；
3. 与分P数无关：1P / 2-5P / 6-20P / >20P 四个区间成功率都在 92–95%，
   没有哪个区间明显塌陷；
4. 44 条散布在第 3–25 页，属于随机失败。

**真实原因（程序侧设计问题）**：

- `UpDownloadBridge.enqueue()` 里取详情失败时是 `Logger.println(...)` + `continue`，
  **静默跳过**，界面不给任何提示；
- 下载失败不写 `repo.config`（只有成功才写），所以事后无从追溯少了哪几条；
- 一次性把 700+ 条任务压进队列、并发抓流地址时，B 站会限流（曾出现 `412`），
  重试 3 次（`bilibili.download.maxFailRetry=3`）仍失败就被丢弃。

也就是说：**不是视频没了，是任务被静默丢掉了**。这 44 条现在已经能在台账里按
`状态=清单` 筛出来，可以重新投递下载。

## 六、补采机制（下载完成 → 自动比对 → 补采清单页二次推送）

### 触发

`DownloadWatch`（守护线程，随程序启动）每 5 秒数一次 `download` 目录的文件数：

- 出现过增长、并连续 **30 秒**不再变化 → 判定这一批下完了，自动跑一次比对
- 两次自动比对之间至少隔 2 分钟，避免反复触发
- 只记账，不碰下载链路；出错只打日志，不会影响主程序

### 口径

- **比对基准 = 最近一次推送的清单**（`记录工具\最近推送.csv`，每次点「加入下载队列」时覆盖写入）
- **落盘侧 = `download` 目录文件名 + `config\repo.config`** 里出现过的所有 BV
- 粒度是 **BV**（一个视频多分P只算一条），和取详情只回 1 个 clip 的行为一致
- 差集写进 `记录工具\补采记录.csv`（状态 `待补`）；下次比对时如果磁盘已经有了，自动改 `已补`

### 补采清单页签

- 表格列：封面 / 标题 / BV号 / 分P / 来源 / 首次发现 / 最近比对 / 状态 / 次数
- 状态染色：待补橙、已补绿、忽略灰
- 按钮：`立即比对`（只比最近一次推送）、`比对全部清单`（把所有 UP 主 checkpoint 一起比）、
  `全选待补`、`加入下载队列`（**二次推送**，复用原有下载链路）、`标记忽略`、`刷新`、`打开CSV`
- 双击一行打开对应 B 站页面
- 推完不用手动收尾：下一批下载结束后自动重新比对，成功的会被标成 `已补`

### 现状

`补采记录.csv` 里已经有 **44 条待补**（UID 634427163 那批清单里没下成的），
打开「补采清单」页 → 点「全选待补」→「加入下载队列」就能重推。

## 七、「按 UP 主建文件夹」为什么失效了（已修复）

**原因：文件名模板被改坏了，是我改的。**

`config\app.config` 里这一行决定文件怎么命名、要不要建子目录：

| 版本 | 模板 |
|---|---|
| 原来的（`app.config.bak` 里保留的） | `(:listName 0_listName\)UpName\avTitle-(:favTime favTime-)pAv2-qn` |
| 被我改坏的（本次修复前） | `(:listName 0_listName\)avId-avTitle-(:favTime favTime-)pAv2-qn` |

我当初为了让文件名带 BV 号（台账脚本靠文件名里的 `BV...` 认视频），把 `UpName\`
删了、改成 `avId-` 前缀。结果文件名有了 BV 号，但 `UpName\` 这个
「UP 主名 + 目录分隔符」丢了，于是 690 个文件全部平铺在 `download` 根目录。

**修复后的模板**（两者兼得）：

```
bilibili.name.format = (:listName 0_listName\)UpName\avId-avTitle-(:favTime favTime-)pAv2-qn
```

实测（headless 调程序自己的 `CmdUtil.genFormatedName`，不是推测）：

`UpName` 字段确认有值：取详情时 `ClipInfo.upName = 完全着衣Sir`

**存量文件已归位**：`download` 根目录 690 个 mp4 逐个核对 BV 后，
确认全部属于 UID 634427163（完全着衣Sir），已整体移到
`download\完全着衣Sir\`，台账同步后路径也更新了（在库 690 条不变）。

## 八、「补采推送了但没到下载页」（已修复）

**现象**：在「补采清单」点「加入下载队列」，状态栏提示"已加入下载队列，共 N 个任务"，
但「下载页」里没有任务、也不开始下载。

**原因**：`DownloadRunnable.run()` 不是纯下载代码，它开头要做两件 Swing 的事：

1. `new DownloadInfoPanel(clip, qn)` 建下载面板
2. 把它挂到 `Global.downloadTab.getJpContent()` 上，并注册进 `Global.downloadTaskList`

这是 UI 操作，**必须在 EDT 里执行**。我原来的桥直接
`Global.queryThreadPool.execute(new DownloadRunnable(...))`，把这段 UI 代码丢到了后台线程，
组件挂不上，任务也就没跑起来。

**修复**：改成 EDT 派发

```java
SwingUtilities.invokeLater(new Runnable() {
    public void run() {
        new DownloadRunnable(infoF, clip, qnF).run();
    }
});
```

**实测证据**（独立进程跑真实链路，不是推测）：

- `enqueue 返回任务数=1`
- 3 秒后 `Global.downloadTaskList` size = **1**（进了下载队列）
- `Global.downloadTab.getJpContent()` 组件数 = **1**（下载页真的挂上了面板）
- 文件落盘：`download\完全着衣Sir\BV1AG8Z6LE1Y-这件竞速泳衣真的太绝了-p01-80.mp4`（3.99 MB）

另外加了投递诊断日志 `记录工具\.push.log`，每次推送都会记录条目数、qn、任务数、
以及登记失败时的异常，下次再出问题可以直接看这个文件。

### 8.1 第二个坑：列错位（同时修掉）

修完 EDT 之后仍然"点了没反应、下载页没数据"。日志救场——`.push.log` 里写的是：

```
开始投递：items=43 qn=80 allPages=false
取详情失败，跳过 2
取详情失败，跳过 11
取详情失败，跳过 423
...
投递结束：任务数=0
```

`跳过 2 / 跳过 423` 是**分P数**，不是 BV 号。也就是说：表格里显示的是「分P」这一列，
程序却把它当成「BV号」取来用，等于拿 `2`、`423` 去 B 站查视频，当然 43 条全部失败、任务数 0。

**根因**：CSV 数据列顺序和界面显示列顺序**不是一回事**。

- CSV（`ShortfallChecker.HEAD`）：`BV号, 标题, 分P数, 清单来源, 清单页码, 首次发现, 最近比对, 状态, 尝试次数`
- 界面（`MakeupPanel.COLS`）：`封面, 标题, BV号, 分P, 来源, 首次发现, 最近比对, 状态, 次数`

原来的 `getValueAt` 直接 `return rows.get(row)[columnIndex]`，把显示列号当数据列号用。
于是「BV号」列（第 2 列）实际显示的是 CSV 第 2 项 = 分P数；推送时 `setBvid(r[COL_BV])`
拿到的也是分P数。同一处错位还连带污染了 `recordPush` 写的推送清单、`markIgnore`、双击跳转、封面取图。

**修法**：在模型入口一次性把 CSV 行转成"显示顺序"，之后所有按列取值都安全
（`MakeupPanel.MakeupModel.toDisplayRow`）：

```java
out[0] = bv;         // 封面用 BV 取图
out[1] = r[1];       // 标题
out[2] = bv;         // BV号
out[3] = r[2];       // 分P数
out[4] = r[3];       // 来源
out[5] = r[5];       // 首次发现
out[6] = r[6];       // 最近比对
out[7] = r[7];       // 状态
out[8] = r[8];       // 次数
```

**实测**（拿一条真实待补项 BV1nu8M6PE8G 走完整链路）：

- 取详情成功（不再"跳过"）
- `enqueue 返回任务数=1`
- 3 秒后 `downloadTaskList` size=1，下载页容器组件数=1
- 落盘 `download\完全着衣Sir\BV1nu8M6PE8G-纯白的舞蹈生-p01-80.mp4`（1.16 MB）

### 8.2 顺手去掉的隐患：「比对全部清单」
